# CCTV person search

Прототип просмотра камер с отдельными слоями захвата, обработки и веб-интерфейса.
Детекция людей включается кнопкой в UI; поиск по личности пока не реализован.
Python 3.13, зависимости и команды через uv.

## Запуск

1. Выполнить `uv sync` (включая инструменты разработки pytest и ruff).
2. Создать локальный `.env` по `.env.example`, заполнить placeholders.
   Старый `.env_example` устарел: использовать имена `USER_CAM` и `PASSWORD_CAM`.
3. Выполнить `uv run main.py`. Открыть localhost на порту `WEB_PORT`.
4. Остановить через Ctrl+C или SIGTERM. HTTP-команда завершения удалена.

Настройки читаются только при явном запуске. Ошибки конфигурации не выводят
значения. `.env` не переопределяет переменные окружения. Конфигурация камер
исключена из repr. Не включайте отладочные логи сторонних видеобиблиотек.

`CAMERA_BACKEND=dvrip` использует отдельное соединение для каждого номера
из `CHANNELS`, общий адрес/порт и учётные данные DVR. Период опроса задаётся
`SNAPSHOT_INTERVAL` (по умолчанию 0.2 секунды плюс длительность запроса).

`CAMERA_BACKEND=rtsp` использует непрерывный поток через PyAV/FFmpeg, TCP,
таймауты открытия/чтения `IO_TIMEOUT`. Для каждого канала нужно задать
`CAMERA_<номер>_RTSP_URL`. Адреса определяются по документации камеры/NVR;
приложение не угадывает их и не сканирует сеть. Кадры на диск не записываются.

## Устройство

- `src/camera/`: контракт источника и адаптеры DVRIP/RTSP, без зависимостей от ML.
- `src/processing/`: нормализованный BGR-кадр, JPEG для просмотра, время получения
  на сервере (не аппаратная метка камеры), буфер последнего кадра.
- `src/application/`: один поток-владелец на источник, reconnect с ограниченной
  экспоненциальной задержкой, остановка и освобождение соединений.
- `src/web/`: фабрика Flask, шаблон страницы, `/channel/<номер>`, `/health`.
- `src/inference/`: YOLO PT, общий ML-worker, отрисовка рамок и управление из UI.

Каждый будущий ML-потребитель может вызывать `manager.frames[channel].wait(after)`
со своим номером последовательности. Медленный потребитель пропускает старые
кадры; память не растёт с длиной очереди. Общий BGR-массив доступен только для
чтения: перед модификацией модель должна сделать копию. Inference следует
запускать отдельным потребителем, а не внутри цикла камеры.

При обрыве буфер очищается. MJPEG не отправляет повторно один кадр и пропускает
просроченные кадры (`STALE_AFTER`). Браузер может продолжать показывать последний
полученный кадр; `/health` возвращает 503 при отсутствии свежих данных хотя бы
одного канала. Клиентское отображение состояния пока не реализовано.

Соединение закрывает его поток, без одновременного close/read из веб-потока.
Остановка будит потребителей и прерывает backoff. После ограниченного ожидания
неостановившийся worker приводит к явной ошибке. Таймауты сетевых библиотек
не являются абсолютной гарантией для DNS и зависшего нативного декодера;
для жёсткого предела завершения захват потребуется вынести в отдельный процесс.

Текущий запуск — один процесс с встроенным Flask-сервером для локальной работы.
Не включать reloader и несколько WSGI workers: буферы находятся в памяти,
а каждый процесс создал бы свои подключения. Production-развёртывание требует
явного владельца захвата и обмена между процессами либо медиа-сервера.

## Непрерывное видео и дальнейшая архитектура

В исходном прототипе JPEG тоже хранился в памяти, а не на диске. Ограничение
состояло в повторных snapshot-запросах вместо чтения непрерывного видео.
RTSP-адаптер устраняет это на входе, но текущий браузерный просмотр всё ещё
использует MJPEG: декодирование и JPEG-кодирование требуют CPU.

Рекомендуемая следующая схема при наличии RTSP у оборудования:

```text
Камера/NVR → RTSP → MediaMTX → WebRTC/HLS → браузер
                         └→ RTSP → Python/PyAV → BGR → ML
```

MediaMTX позволяет принимать RTSP и предоставлять браузерный просмотр:
[введение](https://mediamtx.org/docs/kickoff/introduction),
[WebRTC/HLS в браузере](https://mediamtx.org/docs/read/web-browsers).
WebRTC даёт меньшую задержку; HLS проще по сетевому подключению, но задержка
выше. Совместимость кодеков с браузером проверяется отдельно; при несовместимости
потребуется перекодирование. Это выбор для следующего этапа, сервер сейчас
не устанавливается и не запускается. Адреса камеры и учётные данные должны
оставаться на серверной стороне, не попадать в HTML.

В установленной python-dvr есть `start_monitor`, но его параметры содержат
фиксированный канал 0; переход на него для двух каналов потребовал бы отдельной
проверки протокола и декодирования. RTSP предпочтителен, если поддерживается.
Факт поддержки, кодеки, FPS и задержка конкретных камер пока не проверены.
PyAV поддерживает [таймаут открытия и чтения](https://pyav.org/docs/develop/api/_globals.html).

## Проверки

`uv run ruff check .` и `uv run pytest`.
Тесты используют синтетические изображения и поддельные источники, без `.env`,
секретных переменных и подключений к камерам. Проверяются валидация,
нормализация, fan-out, reconnect, остановка, очистка адаптеров и Flask-маршруты.

## Детекция людей

При каждом запуске детекция **выключена**. Кнопка «Включить детекцию людей»
управляет всеми каналами одновременно. UI показывает загрузку, состояние,
ошибки и количество людей на последнем обработанном кадре каждой камеры.
Это количество детекций, а не уникальных посетителей; трекинга пока нет.

Используются веса YOLOv8 Nano `.pt` через Ultralytics/PyTorch.
`ML_DEVICE=gpu` по умолчанию выбирает первую CUDA-видеокарту; `ML_DEVICE=cpu`
включает CPU. При недоступной CUDA UI показывает ошибку без скрытого перехода на CPU.
Для GPU необходимы совместимые драйвер NVIDIA и сборка PyTorch с CUDA.
На GPU используется FP16 для экономии видеопамяти, на CPU — FP32.
Один экземпляр модели обслуживает обе камеры последовательно. По умолчанию
вход до 320×320 и максимум 2 кадра/сек на камеру; фактическая скорость зависит от устройства.
Это уменьшает нагрузку, но небольшие/далёкие люди могут обнаруживаться хуже.
Веса в репозиторий не включены и автоматически не скачиваются. Без весов UI
показывает сообщение и возвращается к обычному просмотру, не имитируя детекцию.

Установите ML-зависимости и поместите доверенные веса `yolov8n.pt`
в `models/` либо задайте `ML_MODEL_PATH`:

```sh
uv sync --extra ml
uv run --extra ml main.py
```

ML-зависимости выделены в extra `ml`; без него видеопросмотр работает,
а включение модели предлагает установить зависимости. Импорт PyTorch и загрузка
весов происходят только после включения. Модель должна содержать класс `person`.
Предобработку и NMS выполняет Ultralytics, координаты возвращаются в размере
исходного кадра. [Параметры inference](https://docs.ultralytics.com/modes/predict/).

Настройки в локальной конфигурации:

| Переменная | По умолчанию | Значение |
| --- | --- | --- |
| `ML_MODEL_PATH` | `models/yolov8n.pt` | Локальный PT-файл |
| `ML_DEVICE` | `gpu` | `gpu` (CUDA:0) или `cpu` |
| `ML_FPS` | `2` | Максимум кадров/сек с каждой камеры, до 10 |
| `ML_IMAGE_SIZE` | `320` | 320, 416 или 640 |
| `ML_CONFIDENCE` | `0.4` | Порог уверенности от 0 до 1, не включая 0 |

При включённой детекции показывается именно обработанный кадр с его рамками,
без переноса координат на более новое изображение. Поэтому частота обновления
просмотра с рамками ограничена скоростью ML. До первого результата показывается
обычное видео. После выключения сразу очищаются результаты; выполняющийся
inference заканчивается, его результат отбрасывается, модель освобождается.
Прерывание зависшего нативного inference требует завершения процесса; stop
ожидает ML-worker максимум 10 секунд и сообщает об ошибке при превышении.

`GET /api/detection` возвращает состояние; `POST /api/detection` принимает JSON
`{"enabled": true}` или `{"enabled": false}`. Управление общее для всех открытых
страниц одного процесса, состояние синхронизируется опросом. API рассчитан
на текущий локальный режим приложения без пользовательской авторизации.

env -u LD_LIBRARY_PATH -u LD_PRELOAD -u PYTHONPATH     uv run --extra ml main.py
